## 自动采集架构认知修正

背景：用户指出，自动采集在功能上和手动采集是同一件事，不应该被建模成一套独立的采集 pipeline。

我原先的推理错误：

- 我过早聚焦在自动采集的触发机制上：页面识别、`MutationObserver`、路由变化、streaming 稳定判断。
- 因为这些机制看起来是自动采集特有的，我隐含地把自动采集理解成了一条独立 flow。
- 这个理解混淆了两个不同关注点：
  - 触发时机：用户手动点击，还是系统自动检测。
  - 采集行为：提取、标准化、去重、记录 revision、持久化对话数据。
- 正确边界应该是：手动采集和自动采集只在 trigger source 和 capture scope 上不同，它们必须共享同一个 capture engine。

修正后的认知：

- 应该只构建一套统一的 capture pipeline。
- 手动采集和自动采集都只是 trigger mode，最终调用同一个 orchestrator。
- 共享 pipeline 负责 site adapter 选择、message extraction、canonical normalization、dedupe/revision 处理和本地持久化。
- 自动采集应建模为系统触发的调用，例如 `page-detected`、`dom-mutated`、`route-changed`、`conversation-settled`。
- 手动采集应建模为用户触发的调用，例如 `save-current-chat`、`save-selection`、`save-single-message`。
- 这样可以保证行为一致：手动采集能保存的内容，自动采集也能保存；自动采集漏掉时，手动 resync 也能用同一套能力补齐。

设计影响：

```text
Trigger Layer
  -> Capture Orchestrator
  -> Site Adapter
  -> Extractor
  -> Normalizer
  -> Deduper / Revision Manager
  -> Local Sink
  -> Exporter
```

不要创建相互独立的 `manual capture pipeline` 和 `auto capture pipeline`。

## 11:18 - Memory 写入方式修正

Relation:
Supersedes: 自动采集架构认知修正

Signal:

Mistake:
我先前虽然记录了认知修正，但没有使用统一的 distill 结构；记录更像一次性说明，缺少 `Signal`、`Mistake`、`Correction`、`Guardrail`、`Applies` 字段，也没有为同一会话反复调用设计 append-only 语义。

Correction:
记忆沉淀应使用 `feedback-distillation` 的结构化格式。同一日期文件是 append-only ledger；同一会话或同一主题的后续修正也必须追加新 entry，用 `Relation` 标记 `Follow-up` 或 `Supersedes`，而不是回头改写旧内容。

Guardrail:
以后用户明确要求“记下来 / 沉淀 / distill / 反思 / 复盘 / 以后注意”时，先按 `feedback-distillation` 判断是否值得沉淀；若写入 memory，则只追加结构化 entry，并保留旧 entry 作为审查证据。

Applies:
当前 repo 的 `memory/` 记录；所有用户纠偏、反复错误、高摩擦沟通、可复用成功模式的沉淀任务。
