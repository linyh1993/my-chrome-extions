# 2026-08-06

## 11:18 - 自动采集架构认知修正

Relation:
New

Background:
当前 repo 正在讨论一个用于本地归档免费 AI chat 平台对话的 Chrome Extension。目标平台包括 DeepSeek、YuanBao、Google AI Studio、Gemini 等；用户希望支持自动识别、自动触发采集，同时也参考了 `saveai.net` 这类手动导出工具的能力。讨论过程中，我先把 automatic capture 当作一条独立流程来设计，后来用户指出 automatic capture 和 manual capture 在功能上是同一个 capture capability，只是触发方式不同。

Signal:
用户指出“自动采集实际上就是一个功能和手动采集一样的”，随后要求解释为什么我一开始把 automatic capture 想成单独流程，并要求写入 memory。后续用户指出这条记录应该使用 distill 结构；再之后，用户允许按最新 `feedback-distillation` 规则重写日期 memory 文件。

Observation:
我过早聚焦在 automatic capture 的触发机制上，例如页面识别、`MutationObserver`、SPA route change 和 streaming stabilization。因为这些机制看起来是 automatic capture 特有的，我隐含地把 automatic capture 建模成独立 flow，混淆了 trigger timing 和 capture behavior 两个关注点。第一次写入 memory 时，我也没有使用稳定的 distill contract，而是写成普通说明，导致后续又产生一次关于 memory 写法的高摩擦修正。这个过程暴露出一个 skill opportunity：用户纠偏信号需要被统一蒸馏为可审查字段，而不是临时写成叙述。

Correction:
manual capture 和 automatic capture 只应在 trigger source 与 capture scope 上不同，不应该分裂成两条 capture pipeline。系统应构建一个统一的 capture engine，由 manual trigger、auto trigger、selection trigger、single-message trigger 等入口调用同一个 orchestrator。memory 记录应使用 `feedback-distillation` 的后置结构：`Signal`、`Observation`、`Correction`、`Guardrail`、`Applies`。

Guardrail:
设计功能时，先区分“触发方式”和“业务能力”。如果两个入口最终要完成同一种用户可见能力，默认建模为不同 trigger 调用同一套 capability pipeline，不要因为触发机制不同而创建重复流程。用户要求“记下来 / 沉淀 / distill / 反思 / 复盘 / 以后注意”时，先使用 `feedback-distillation`；除非用户明确授权重写，否则 memory 写入默认 append-only。

Applies:
当前 repo 的 AI chat archive 设计；Chrome Extension 中 manual/auto trigger 与 shared capture engine 的架构讨论；所有需要把用户纠偏、反复错误、高摩擦点或 skill opportunity 沉淀为可审查 memory 的任务。
