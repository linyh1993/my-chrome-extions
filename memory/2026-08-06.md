## Auto capture architecture correction

Context: The user pointed out that automatic capture is functionally the same as manual capture. It should not be treated as a separate capture pipeline.

My original reasoning mistake:

- I focused too early on the trigger mechanics of automatic capture: page detection, `MutationObserver`, route changes, and streaming stabilization.
- Because those mechanics are specific to auto capture, I implicitly framed auto capture as a separate flow.
- That framing mixed two different concerns:
  - trigger timing: manual click vs automatic detection
  - capture behavior: extracting, normalizing, deduplicating, and storing conversation data
- The correct boundary is that manual and automatic capture differ only in trigger source and capture scope. They must share the same capture engine.

Corrected understanding:

- Build one unified capture pipeline.
- Manual capture and automatic capture are both trigger modes that call the same orchestrator.
- The shared pipeline should own site adapter selection, message extraction, canonical normalization, dedupe/revision handling, and local persistence.
- Auto capture should be modeled as system-triggered calls such as `page-detected`, `dom-mutated`, `route-changed`, or `conversation-settled`.
- Manual capture should be modeled as user-triggered calls such as `save-current-chat`, `save-selection`, or `save-single-message`.
- This keeps behavior consistent: anything manual capture can save, auto capture can also save, and manual resync can repair auto-capture misses.

Design implication:

```text
Trigger Layer
  -> Capture Orchestrator
  -> Site Adapter
  -> Extractor
  -> Normalizer
  -> Deduper / Revision Manager
  -> Local Sink
  -> Exporter
```

Do not create separate `manual capture pipeline` and `auto capture pipeline`.
