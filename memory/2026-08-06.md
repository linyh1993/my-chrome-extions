## 11:18 - 自动采集架构认知修正

Relation:
New

Signal:
用户指出“自动采集实际上就是一个功能和手动采集一样的”，随后要求解释为什么我一开始把自动采集想成单独流程，并要求写入记忆文件。后续用户又指出这条记忆应该使用 distill 结构，而不是普通说明式记录。

Mistake:
我过早聚焦在自动采集的触发机制上，例如页面识别、`MutationObserver`、SPA route change 和 streaming stabilization。因为这些机制看起来是自动采集特有的，我隐含地把 automatic capture 建模成独立 flow，混淆了 trigger timing 和 capture behavior 两个关注点。第一次写入 memory 时，我又把这次纠偏写成普通叙述，缺少 `Signal`、`Mistake`、`Correction`、`Guardrail`、`Applies` 这类可审查字段。

Correction:
manual capture 和 automatic capture 只应在 trigger source 与 capture scope 上不同，不应该分裂成两条 capture pipeline。系统应构建一个统一的 capture engine，由 manual trigger、auto trigger、selection trigger、single-message trigger 等入口调用同一个 orchestrator。memory 记录也应使用 `feedback-distillation` 的结构化格式，让后续审查能直接看到信号、错误、修正、guardrail 和适用范围。

Guardrail:
设计功能时，先区分“触发方式”和“业务能力”。如果两个入口最终要完成同一种用户可见能力，默认建模为不同 trigger 调用同一套 capability pipeline，不要因为触发机制不同而创建重复流程。用户要求“记下来 / 沉淀 / distill / 反思 / 复盘 / 以后注意”时，先使用 `feedback-distillation` 结构；除非用户明确授权重写，否则 memory 写入默认 append-only。

Applies:
当前 repo 的 AI chat archive 设计；Chrome Extension 中 manual/auto trigger 与 shared capture engine 的架构讨论；所有需要把用户纠偏沉淀为可审查 memory 的任务。
